# 调试经验教训与排障方法论

> 细则文件。由 AGENTS.md 任务路由表加载（排障/debug 类任务）。
> 标记规则：【强制】违反即违纪；【应当】偏离需说明；【可选】无后果。
> 性质：项目级排障纪律，每次排障任务建议执行；复杂 bug（反复试错、现象与预期矛盾）【强制】执行。

## 适用范围

- 典型场景：线上 bug、测试失败、现象异常、功能"消失/失灵"、性能问题。
- 判定不清是否适用时，按适用处理（排障方法论零成本，宁可用上）。

---

## 零、GUI 运行时验证（视觉路由归全局规则）

> 界面/视觉类运行时验证由谁执行（多模态子智能体端到端验证，或多模态主模型自行验证），遵循运行环境已配置的视觉任务路由规则（如用户级 AGENTS.md）；未配置时由当前会话按可用能力安排，本文件不维护按 AI 是否多模态判定的分工逻辑。

### 判定：本任务"是否可能需要 GUI 检查"

收到排障/界面改动类任务后，先判定是否"可能需要 GUI 检查"（改了窗口/控件/样式/动画且需看运行时表现，或排查界面 bug）。判定为是 → 按全局视觉路由分派执行，并遵守下方验证纪律。

### 验证纪律（对执行视觉验证的任何智能体生效）

- 【应当】先确认程序可运行：启动方式、数据源路径、被验证窗口的屏幕位置。
- 【强制】不得影响用户正在使用的环境：验证只在本地运行程序实例，不注册自启动、不改用户系统设置。
- 【强制】结论必须以实际截图/运行日志为证据，不得以"程序能启动/窗口能打开"作为行为正确的证据。
- 【强制】自动化连续失败超 2 回合仍拿不到关键信息 → 停下向用户说明，回落请用户手动验证并反馈运行日志/报错。
- 【强制】回落用户手验时，对"怎么验证"负责：给出具体、可执行的操作步骤（哪个窗口、哪个控件、预期看到什么）；需要运行时数据时设计带唯一标记的临时探针（如在可疑函数前加 `print('PROBE-X', 变量)`），并说明"最后一条 PROBE 之后紧跟的报错就是根因"。
- 【强制】探针用完即清，不得留在提交里（提交前用搜索兜底查 `PROBE`/`print(`）。

## 一、三条铁律（违反就是方法论违纪）

### 铁律 1：动手前先复现，不接受他人对现象的"解释"

【强制】调试第一步永远是**亲自复现、观察原始现象**，不是接受用户或他人对现象的结论性描述。

- 用户说"功能消失了"，这是**结论**；事实应是"我在 X 界面点 Y 按钮，没看到 Z"。
- 【强制】收到 bug 报告后，先在本地复现并记录**精确现象**（哪个窗口、哪个控件、什么状态），再开始查因。未复现就开查 = 在猜。

> 反面教训：接受"功能丢失"前提一头扎进 git 历史考古，绕一大圈；其实只要先看控件树状态，几分钟就能发现"控件对象还在，是被 setVisible(False) 或布局压成 0 尺寸了"，根本不走 git 考古方向。

### 铁律 2：新证据与旧假设矛盾时，立刻丢弃假设

【强制】当收集到的新证据与当前假设冲突，必须**立刻推翻假设**，不得修补旧假设强行自圆其说。

- 假设是工具不是信仰。证据说了算。
- 【强制】若发现自己在"为旧假设打补丁、找理由解释矛盾"，立即停下，回到证据重新归因。

### 铁律 3：代码"看起来对但行为不对"时，停止读代码，去运行时抓数据

【强制】当静态阅读代码逻辑自洽、但运行行为不符时，**不要再反复读代码**，改用运行时插桩抓真实执行数据。

- 适用场景：逻辑明明对、就是不出预期结果；反复读同一段代码找不出问题。
- 【强制】这类情况根因几乎一定在"运行时的实际值"（控件属性、函数入参、变量类型、执行时序），而静态阅读看不到这些。

> 反面教训：函数逻辑反复读多遍都"对"；最后用运行时插桩才抓到实际传入的控件引用是 None（父对象被提前析构）。静态阅读永远抓不到这个。

## 二、控件"显隐/状态异常"标准排查顺序（Qt 桌面）

适用：控件该显示却不显示、该隐藏却不隐藏、按钮"消失"、区域不见、数值不刷新等。

【强制】严格按以下顺序，不得跳步、不得先怀疑数据源：

### 第 1 步：看控件对象在不在、当前属性是什么

- 打印/断点检查控件对象是否存在（是否为 None、是否已被析构）。
- **控件不存在/为 None** → 构建路径没走到 → 查构建条件、父对象归属、是否被异常吞没跳过。
- **控件存在但不可见** → 是 `setVisible()`/样式控制 → 进第 2 步。

### 第 2 步：定位显隐/状态控制源（谁改的）

- 查 `setVisible()`/`hide()`/`show()` 调用点；同时检查控件是否被布局压缩为 0 尺寸（QSS 的 display 类规则在 Qt 上语义有限）。
- 区分是构建时写死隐藏，还是信号槽/定时器在运行时切换。

### 第 3 步：运行时插桩，抓"谁在何时改了状态"

- 在可疑调用点包一层打印（`print('PROBE-X', 控件, 值)`），或给相关信号临时 `connect` 一个打印槽，记录触发时机与入参。
- 对"数值不刷新"类问题分两段验证：先打印轮询回调原始数据（确认数据源产生了新值），再打印 setText 前的值（确认 UI 层执行了更新）。
- 【强制】这一步是抓"行为不对"类 bug 的杀手锏，逻辑矛盾时必上。

### 第 4 步：最后才怀疑数据源

- 前三步走完确认控件构建与状态切换都正常，仍异常，才查 SQLite 查询结果、聚合口径。

## 三、运行时插桩常用手法

| 排查目标 | 插桩手法 |
|---------|---------|
| 谁改了控件可见性 | 包装/替换 `setVisible`/`hide`/`show` 调用，记录控件 + 调用栈 |
| 信号到底发没发、带了什么 | 临时 `connect` 打印槽，记录发射次数与参数 |
| 函数实际收到什么参数 | 在调用点包一层，记录入参实际值与类型 |
| 某操作何时发生 | 用 `time.perf_counter()`/`QElapsedTimer` 打时间戳，对比多个操作的时序 |
| 定时器轮询是否按预期跑 | 计数 QTimer 回调次数与间隔，确认异常未被静默吞掉导致停摆 |

> 涉及 Qt 内部事件时序时，可在 `QApplication.notify` 外包一层记录事件序列，适合抓加载早期的时序问题。

## 四、调试纪律红线

- 【强制】**不得"先改了试试看"**。任何修改前必须有明确的根因假设。
- 【强制】**不得同时改多处再测**。一次只验证一个变量，否则无法定位是哪个改动起效。
- 【强制】**修复后必须回归验证**。改完要在本地复现场景确认已修复，并检查是否引入新问题。
- 【应当】复杂 bug 定位后，把"根因+排查路径"简要记入本文件案例库，沉淀经验。

## 五、经验案例库（随项目持续积累）

> 每个项目自己的案例写在这里。条目格式：现象 → 错误路径 → 正确路径 → 根因 → 教训。
> 以下是源项目沉淀的通用化教训（已抹去业务细节），对多数项目成立：

### 通用教训 1：元素"消失"先看 DOM，不要先考古历史

元素 HTML 还在但被 class 隐藏 ≠ 服务端没渲染；选择器字符串拼接缺字符会匹配 0 个元素，"全部隐藏"生效而"目标显示"失效。静态阅读抓不到字符串拼接问题，运行时拦截选择器入口一次定位。

### 通用教训 2：修复前端 bug 后，要在原触发边界条件上回归

潜伏 bug（只在特定边界触发，如"首期/首次/为空"）被其他修复暴露后，只在常规路径验证会漏。回归要覆盖触发条件本身。

### 通用教训 3：多个后端校验共用同一错误协议时，前端必须分类处理

前端一个 catch 把所有同类错误码拼成同一文案，会误报并堵死用户自救路径。新增校验类型时同步检查前端错误呈现分支。

### 通用教训 4：保存链路必须同步重算模板直接渲染的派生字段（仅适用于该架构）

适用于"模板直接渲染派生字段"的架构：只存主字段、不重算派生字段（各类由主字段推导出的展示值），恢复后页面显示旧值。恢复链路若不做重算（原样落盘），保存链路就是唯一同步点。"保存→恢复→渲染"链路要逐段核对类型口径（字符串 vs 数值）。

### 通用教训 6：非 ASCII 注释 + 按 ANSI 读取的脚本运行时，中文注释会毁掉整个脚本

wscript 按 ANSI(GBK) 读 .vbs，UTF-8 无 BOM 的中文注释字节被误解析后，报错却是注释之后正常代码的"缺少对象"——错误位置与真实根因错位。同类：bat 的中文输出在代码页不符时乱码。启动器脚本一律全 ASCII；含中文的路径用环境变量展开（ExpandEnvironmentStrings("%LOCALAPPDATA%…")），不硬编码。另一坑：PATH 上的 python/pythonw 可能指向其他 venv（本机 hermes venv 实测），GUI 启动器必须用绝对解释器路径。两个坑叠加的表现就是"双击闪退、直跑正常"。

### 通用教训 5：取证优先于推断

用户现场的精确数据（操作日志、临时文件、真实输入快照）比代码逻辑推断更值钱。先取这些再谈假设。
