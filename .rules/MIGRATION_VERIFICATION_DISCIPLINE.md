# 方案执行防偏离工作纪律

> 细则文件。由 AGENTS.md 任务路由表加载（方案/设计文档实施类任务）。
> 标记规则：【强制】违反即违纪；【应当】偏离需说明；【可选】无后果。
> 性质：由 `AGENTS.md`（AI 执行规则）路由后生效的项目级强制纪律；每次方案类任务必须执行。

## 适用范围

【强制】任何基于设计文档/方案文档执行的实施任务都适用。判定不清是否为"方案类"时，按方案类处理（宁可多读）。

- 典型场景：数据库结构变更、数据迁移、一步切换、跨模块共享接口改造等。
- 不适用：日常 bug 修复、小范围功能调整、纯查询类任务。

## 四道纪律（每次方案任务必须执行，缺一不算完成）

### 纪律 1：动工前先产出"完成定义"，不是"功能清单"

todo 回答"做什么"，完成定义回答"做到什么程度才算真完成"。

【强制】从方案文档中提取两类硬约束，写成可核对断言（写到本任务执行记录，不写进本通用文档）：

```
方案:<文档路径>
正向断言:
  - [ ] <方案原句,即"必须/应当/需要"> → <验证方式>
反向断言:
  - [ ] <方案原句,即"不得/禁止/停止/不再/唯一"> → <验证方式>
```

- 【强制】重点抓反向断言（偏离高发区）。"不得保留旧入口""停止使用旧表""唯一事实来源"等表述，方案意图是"切断"，绝不允许降级为"保留兜底"。
- 【强制】自检：如果删掉所有反向断言对应的代码，这个任务还能算完成吗？不能则完成定义漏了。

### 纪律 2：维护"禁用清单"，和 todo 清单同等重要

方案里"一步切换/停止使用/替代"等表述，等价于一张禁用清单。

【强制】把禁用清单写成显式表格，每条标注验证状态（脑子里的清单不算数，只有写下来才能被核对）：

| 旧入口/旧字段 | 方案要求 | 当前是否仍被写入 | 调用点已排查 | 反向测试已加 |
|--------------|---------|----------------|-----------|------------|
| （按具体方案填） | 停止使用 | ❓ | [ ] | [ ] |

- 【强制】禁止给禁用清单里的旧入口"加兜底/镜像写入/回退兼容"。方案要求停用就是停用。判断风险高时必须向用户提出，由用户决定，不得自行降级。

### 纪律 3：写反向测试，不只写正向测试

正向测试问"功能在吗"，反向测试问"禁用的东西还在吗"。前者无法发现偏离，后者才能。

【强制】为反向断言和禁用清单的每一项写反向测试。典型模式（示例，按项目测试框架改写）：

```python
# 反向测试:验证旧入口运行时不再被写入
def test_legacy_X_not_written_at_runtime():
    """运行时执行 Y 操作,X 表不应留下任何新记录"""

# 反向测试:验证配置不再保存旧字段
def test_config_does_not_persist_deprecated_fields():
    """保存配置后,不应包含 <字段>"""

# 反向测试:验证未确认时不动数据
def test_action_without_confirm_changes_nothing():
    """未确认时执行 X,状态应完全不变"""

# 一致性测试:迁移前后结果一致(涉及数据迁移时)
def test_result_unchanged_after_migration():
    """同一份输入,迁移前后 <输出> 完全一致"""
```

- 【强制】自检：如果偏离再次发生（旧入口又被悄悄启用），测试套件会不会红？不会则反向测试不够。

### 纪律 4：汇报前做偏离自检，且必须诚实

【强制】禁止用"测试通过 + 功能齐全"作为完成判据。完成的真正标准是"方案每条要求都被满足，方案禁止的每件事都没做"。

【强制】汇报前必须回答三个问题，并在汇报中显式包含答案：

1. **正向核对**：方案里所有"必须"的，哪些没实现？（逐条勾对，不允许笼统说"已全部实现"）
2. **反向核对**：方案里所有"不得/停止"的，哪些还在做？（必须主动找，找过就说找过，包括"我没找到"）
3. **主动降级检测**：我有没有在某处添加了方案没要求的东西？（"为了兼容/为了安全"加的兜底、镜像、回退都算）

- 【强制】汇报必须包含一节"偏离自检"，即使结论是"未发现偏离"也要写明核对范围，不允许省略。

## 执行时机

| 阶段 | 必做动作 |
|------|---------|
| 读方案后、动工前 | 产出完成定义（正向断言 + 反向断言）和禁用清单，写到本任务执行记录 |
| 排查代码依赖时 | 每发现一个旧入口被使用，登记进禁用清单，禁止就地"加兜底" |
| 写测试时 | 每个反向断言至少一条反向测试 |
| 汇报前 | 执行纪律 4 的偏离自检，写入汇报的"偏离自检"节 |
| 用户二次审查后 | 如果审查发现偏离，对照本纪律回溯是哪一道失效了，补进本文档（不是只修这次的代码） |

## 必须停下来确认的情况（避免自己悄悄降级）

遇到以下任何一种情况，【强制】禁止自行决定，必须向用户提出：

1. 方案要求停用某个旧入口，但该入口被 ≥2 处依赖，且不在方案明确范围内。
2. 想给禁用清单里的旧入口"加兜底/保留兼容"。
3. 方案要求"一步切换"，但判断风险高想改成分阶段。
4. 发现方案某处和现有代码冲突，方案没明确说明怎么处理。
5. 测试全绿但反向断言无法全部验证（说明测试覆盖不够，不是任务完成）。

规则：宁可多问，不可自作主张降级。

## 元规则

1. 【强制】本纪律适用于所有方案类任务。不确定算不算"方案类"，按算处理。
2. 【强制】本纪律不可被绕过。觉得某道纪律对某任务不适用，必须向用户说明并获明确同意，不允许自行豁免。
3. 【强制】偏离被发现后，修的是机制不是只修代码。每次审查发现偏离，回溯是纪律 1-4 哪一道失效，把失效原因补进本纪律或加测试，防止同类问题再次无声发生。
4. 【强制】"看起来完成"不等于"完成"。测试全绿、功能齐全、代码自洽，都不能单独作为完成判据；必须叠加完成定义核对 + 反向测试通过 + 偏离自检。

## 附：历史背景（非指令，仅供理解本纪律为何存在）

> 以下内容为叙述性背景，不构成可执行指令。指令以正文四道纪律为准。

创建背景：一次真实方案实施出现系统性偏离——方案要求"一步切换"，实际实现成"新旧事实并存"，且在几十个测试全绿的情况下仍未被发现，最终靠二次审查才暴露。本纪律是为了让这类偏离在**实现阶段就被自己发现**，而不是依赖外部审查兜底。

典型失败模式：

1. 读方案 → 理解成"加新结构/新功能"，而非"替换旧事实来源"。
2. 实施时遇到旧代码依赖 → 触发风险规避本能 → 无声地降级为"加兜底/保留旧入口/镜像写入"。
3. 测试只验证"我写的代码自洽"，不验证"方案禁止的东西还在不在"。
4. 汇报以"测试全绿 + 功能齐全"为完成标志，偏离带着光环进生产。

根因：偏离发生在意识层之下，没有外部约束让它可见。靠"下次更小心"无效。本纪律提供四个外部约束，强制让偏离变成可见信号。
